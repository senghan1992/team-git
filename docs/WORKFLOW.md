# 팀 작업 흐름 (Git Companion)

이 문서는 "한 프로젝트를 여러 사람이 각자 브랜치에서 작업하고, 병합 관리자가
병합 브랜치로 모아 준다"는 하나의 흐름을 앱 화면과 1:1로 짝지어 설명한다.
새로 합류한 팀원은 자기 역할에 해당하는 절만 읽으면 된다.

---

## 등장인물

| 역할 | 하는 일 | 주로 보는 화면 |
| --- | --- | --- |
| **팀원** | 내 브랜치에서 작업 → 커밋 → 내 원격 브랜치로 push → 병합된 내용을 동기화 | 저장소 → **작업** 탭 |
| **병합 관리자** | 팀원이 push한 브랜치를 병합 브랜치(main 등)로 병합 → push | 저장소 → **병합** 탭 |

관리자는 `.gpconfig`의 `merge_managers`에서 **브랜치별로** 지정한다
(저장소 → **설정** 탭). 지정하지 않으면 누구나 병합할 수 있다.

### 0. 앱을 열면 먼저 로그인한다

앱을 켜면 **로그인 화면**이 나오고, 로그인해야 안으로 들어갈 수 있다. 이 앱은
팀이 함께 쓰는 도구라 "누가 병합 관리자인가", "이 push 알림은 누구 것인가"가
전부 계정의 **이메일**로 판정되기 때문이다. 로그인은 **한 번만** 하면
재시작·오프라인에도 유지되고, 로그아웃하면 다시 이 화면으로 돌아온다.

### 0-1. 계정 만들기

계정은 **팀 서버**에 저장되므로, 팀에서 서버 하나를 띄우고 각자 회원가입한다.
서버는 팀에서 한 사람이 띄운다 —
[README의 "0-1. 팀 서버 띄우기"](../README.md#0-1-팀-서버-띄우기--팀에서-한-사람만-한-번만)
를 그대로 따르면 된다.

로그인 화면의 **서버 주소**에 그 주소(`http://서버IP:8000`)를 넣고 **연결
확인**이 되면, **계정 만들기** → 이름·이메일·아이디·비밀번호를 등록하면 바로
로그인된다.

**이메일이 곧 팀 안의 신분이다.** 병합 관리자 지정과 구성원 목록(`.gpconfig`),
알림 수신자가 모두 이메일로 매칭되므로, 팀에서 쓰는 이메일로 가입한다.

로그인은 한 번만 하면 유지되고(재시작·오프라인 포함), 사이드바의 내 이름을
누르면 마이페이지에서 프로필·비밀번호를 바꾸거나 로그아웃할 수 있다.

### 화면이 세 개뿐인 이유

| 사이드바 | 무엇을 위한 곳 |
| --- | --- |
| **저장소** | 내가 지금 무엇을 해야 하는지 (다음 할 일) + 작업/병합/팀 규칙 |
| **알림** | 팀원 소식을 받는 곳. 받은 알림 + 배달망 설정 |
| **설정** | 내 컴퓨터 쪽 설정 (AI, SSH, 자격증명) |

**사람·권한은 저장소 → 설정 탭 한 곳에서만 정한다.** 알림 화면에도 수신자
목록이 있지만 그건 `.gpconfig`를 알림 서버에 반영한 사본이고, 버튼 한 번으로
동기화한다.

```
  │ 2. 작업·커밋   │  ── push ─▶│     기다립니다"       │        │    반영됨"    │
  │ 3. push       │            │ 5. 변경 지도 확인 →   │─push─▶ │ 7. 동기화     │
  └───────────────┘            │    병합 → (충돌 시    │        └──────────────┘

                               │    push               │               ▼
                               └──────────────────────┘        다시 1~3으로
```

## 팀원

### 1. 내 작업 브랜치 만들기

저장소 → **작업** 탭 → **새 브랜치**.

- 현재 브랜치에서 갈라져 나오고, 만든 즉시 그 브랜치로 전환된다.
- **생성 후 원격에 push**를 켜 두면 곧바로 원격 브랜치가 생기고 팀원들이 볼 수 있다.
- 이름은 팀원끼리 겹치지 않게 정한다 (`feature/login`, `fix/nav` 처럼).

### 2. 작업하고 커밋하기

- 상태 표가 변경된 파일을 보여 준다. 파일 이름을 누르면 **diff 미리보기**가 열린다.
- 체크박스로 커밋할 파일만 고를 수 있고, 아무것도 안 고르면 전체가 들어간다.
- **커밋** → 메시지 입력.

### 3. 내 원격 브랜치로 push

**푸시**를 누르면 끝난다. HTTPS 원격이면 처음 한 번 아이디/비밀번호를 묻고
그 뒤로는 저장된 값을 쓴다 (설정 → 푸시 자격증명).

> push 순간 pre-push hook이 이벤트를 보내고, **그 브랜치의 병합 관리자에게만**
> 알림이 간다. 관리자가 아닌 팀원에게는 소음이 되지 않도록 알리지 않는다.

### 6~7. 병합 알림 받고 동기화하기

관리자가 병합 브랜치에 push하면 오른쪽 아래에

> **○○ 저장소에 새 병합이 반영되었습니다** — [내 브랜치에 동기화]

알림이 뜬다. 버튼 한 번으로 `origin/<병합 브랜치>`를 내 브랜치에 병합한다.
충돌이 나면 자동으로 **병합** 탭으로 넘어가 같은 해결 화면에서 처리한다.
**AI 자동 병합의 “충돌이 나면 곧바로 자동 해결”이 켜져 있으면** 이 단계도
버튼 없이 저절로 풀리고 커밋된다 — 해결 못 한 파일만 화면에 남는다.

같은 일을 홈 화면의 저장소 카드 **다음 할 일**에서도 할 수 있다.
그 카드가 "최신 N개 가져오기"를 보여 주면 눌러서 바로 동기화된다.

## 병합 관리자

### 4. push 알림 받기

팀원이 자기 브랜치를 push하면

> **○○: feature/login 브랜치가 병합을 기다립니다** — [병합하기]

알림이 **어느 화면에 있든** 오른쪽 아래에 뜬다. 홈 화면 저장소 카드에도
**다음 할 일: N건 병합하기**로 남는다. 사이드바 **알림** 배지에는 읽지 않은
이벤트 수가 쌓인다.

- 한 번에 뜨는 행동 알림은 **3건까지**다. 자리를 비운 사이 더 쌓였으면 "읽지
  않은 팀 알림이 N건 더 있습니다" 한 줄로 묶여 **알림 보기**로 이어진다.
- 알림 탭에서는 카드마다 **읽음 표시**, 위쪽의 **모두 읽음**으로 정리한다.
  알림의 버튼(병합하기, 내 브랜치에 동기화)을 눌러 처리하면 자동으로 읽음이
  된다. 실패한 동기화는 읽음 처리하지 않는다 — 아직 할 일이다.
- 내 push 알림은 나에게 뜨지 않고, 관리자가 따로 있는 브랜치의 push 알림은
  관리자에게만 뜬다(다른 사람에게는 읽음 상태로 기록만 남는다).

### 5-0. 지난 7일이 어떻게 흘렀는지 — 병합 흐름

**병합** 탭 맨 위 **최근 7일 병합 흐름**은 가로축이 시간이고 맨 아래 줄이
병합 대상 브랜치(main)다.

- 병합된 브랜치는 **첫 커밋 시점부터 main에 합류하는 곡선**으로 그려진다.
  레이블에 브랜치 이름 · 커밋 수 · 파일 수가 붙고, 누르면 커밋 목록과 수정한
  파일이 펼쳐진다 — "이번 주에 무엇이 들어왔나"를 커밋 로그 없이 본다.
- 아직 병합되지 않은 브랜치는 **오른쪽 끝(지금)까지 이어지는 점선**에 "병합
  대기"가 붙는다. 오래 열려 있는 브랜치가 한눈에 드러난다.
- main에 직접 들어온 커밋은 줄 위의 작은 점이다.
- 오른쪽 위에서 **7일 / 14일 / 30일**로 기간을 바꿀 수 있다. 20초마다 자동
  감지되는 새 push 도 여기 반영된다.

### 5-a. 무엇이 바뀌고 있는지 먼저 본다 — 변경 지도

**병합** 탭 상단의 **변경 지도**는 브랜치별 목록을 **파일 기준으로 뒤집어**
보여 준다.

```
변경 지도
대기 중인 브랜치 3개가 파일 6개를 수정하고 있습니다.

⚠ 같은 파일을 두 곳 이상에서 고치고 있습니다 — 1개
  먼저 병합한 쪽이 기준이 됩니다. 나중에 병합하는 브랜치에서 충돌이 날
  가능성이 높으니, 아래 파일들을 확인하고 순서를 정하세요.

⚠ src/api/user.ts    수정·feature/login(김민지)  수정·feature/payment(박준호)
  src/auth/token.ts  추가·feature/login(김민지)
  src/pay/retry.ts   추가·feature/payment(박준호)
```

AI 에이전트로 개발하면 각자 담당 영역 밖까지 함께 수정되는 일이 잦다.
브랜치별 파일 목록만 보면 그 위험이 안 보이므로, **여러 브랜치가 손댄 파일을
맨 위에 세운다.** 기본은 겹치는 파일만 보여 주고, 버튼으로 전체를 펼친다.

겹침이 있으면 **권장 순서**도 함께 제안한다 — 겹치는 파일이 적은 브랜치부터
병합하면 충돌 해결이 마지막 병합 한 곳에 모인다 (같은 파일의 충돌을 병합마다
다시 풀지 않는다). 동률이면 먼저 push된 브랜치부터.

```
권장 순서: fix/nav → feature/login → feature/payment
```

### 5-b. 병합하기

브랜치 카드의 **`<병합 브랜치>`(으)로 병합**을 누른다. 카드에는 작성자,
시간, 커밋 제목, `↑앞선 커밋 / ↓뒤처진 커밋`, 변경 파일, 접히는 커밋 목록이
있다. **자동 감지(20초)**가 켜져 있으면 팀원의 새 push가 저절로 올라온다.

파일 이름만 보고 병합을 결정할 필요는 없다 — 카드의 **파일 칩을 누르면**
그 파일이 병합 브랜치와 어떻게 다른지 diff로 보여 준다.

### 5-c. 충돌이 나면 — AI가 알아서 고치게 하기

**설정 → AI 자동 병합**에서 미리 정해 둔다.

| 항목 | 뜻 |
| --- | --- |
| **AI 사용함** | OpenAI 호환 `/chat/completions` 엔드포인트를 쓴다 (Base URL·모델·API 키). |
| **충돌이 나면 곧바로 자동 해결** | 병합이 충돌로 멈추는 순간(관리자의 병합이든 **팀원의 동기화든**), 버튼을 누르지 않아도 아래 지침대로 바로 고치고 병합 커밋까지 만든다. |
| **자동 해결 후 곧바로 push** | AI가 고친 병합도 확인 단계 없이 병합 브랜치에 push하고 팀원에게 동기화 알림을 보낸다 — 해결 → 커밋 → push가 완전 자동으로 돈다. 끄면(기본) 결과 모달에서 “확인했어요 — push”를 눌러야 팀에 반영된다. |
| **해결 지침(프롬프트)** | 충돌마다 AI에게 보내는 지침. **미리 저장해 두는 것이 핵심이다** — 충돌이 난 순간에 프롬프트를 고민할 필요가 없다. |
| **바이너리·대용량 파일** | diff를 못 만드는 파일은 어느 쪽을 그대로 쓸지 (기본: 상대 것). |

지침에는 팀 규칙을 적는다. 예:

```
양쪽 브랜치에서 수정한 기능이 서로 영향받지 않도록 모두 반영하는 최종 코드를
만들어라. import/선언 누락, 중복 정의, 끊긴 호출부가 없어야 한다.
- 공용 API 시그니처는 theirs(가져온 브랜치) 쪽을 따른다.
- DB 마이그레이션 파일은 절대 합치지 말고 양쪽을 모두 남긴다.
- 주석 없이 코드만 반환한다.
```

비워 두면 기본 지침을 쓴다. **기본값으로** 버튼으로 언제든 되돌릴 수 있다.

자동 해결이 꺼져 있으면 병합 탭의 **AI 자동 병합** 버튼으로 직접 실행한다.
AI를 아예 안 쓰면 규칙 기반(나의 것/상대 것)으로 처리한다.

**안전장치 — 자동 해결이 마음대로 망가뜨릴 수 없다:**

0. **AI가 파일을 고쳐 커밋한 병합은 기본적으로 곧바로 push하지 않는다.** 결과 모달에서
   해결된 파일을 확인하고 **확인했어요 — push**를 눌러야 팀원에게 전달된다.
   (한쪽만 고친 파일을 규칙대로 고른 병합은 잃는 것이 없으므로 바로 push한다.)
   완전 자동 루프를 원하는 팀은 설정의 **자동 해결 후 곧바로 push**를 켜면 된다 —
   그때는 무슨 충돌을 어떻게 풀었는지 병합 커밋 본문에 기록해 두므로
   git log로 언제든 추적할 수 있다.
1. 손대기 전에 충돌 파일 전체를 로컬에 **백업**한다 (병합 탭에서 복원 가능 —
   커밋된 뒤에도 24시간 동안 복원 카드가 남는다).
2. 충돌 표시(`<<<<<<<` 등)가 한 줄이라도 남은 파일은 **절대 커밋하지 않는다.**
3. **AI가 못 고친 파일을 통째로 한쪽만 남기지 않는다.** 양쪽이 모두 고친
   파일에서 한쪽을 고르면 팀원의 커밋이 조용히 사라진 채 push된다. 그래서
   AI가 켜져 있는데 결과를 쓸 수 없으면 그 파일은 충돌 상태로 남기고 사람에게
   넘긴다. (한쪽만 고친 파일은 그쪽을 고르는 것이 곧 정답이므로 그대로
   처리한다.) AI를 끄고 규칙 기반 모드를 직접 실행한 경우에는 요청한 대로
   한쪽을 고른다 — 이때는 사라지는 쪽이 있다는 안내가 화면에 나온다.
4. 일부만 풀렸으면 나머지는 블록 단위 수동 해결(나의 것/상대 것/직접 편집,
   블록별 AI 제안, 되돌리기) 화면으로 넘긴다. 자동 해결은 병합당 한 번만
   돈다 — 실패해도 스스로 몇 번이고 재시도해 화면을 뒤덮지 않는다.
5. 실패해도 `MERGE_HEAD`를 그대로 두므로 이어서 끝낼 수 있다.

### 5-d. push

병합 커밋이 만들어지면 곧바로 push를 시도하고, 실패·취소하면 초록 배너로
재시도 버튼이 남는다. push가 성공하면 팀원 전원에게 동기화 알림이 간다.

배너는 화면을 떠났다 돌아오거나 앱을 재시작해도 다시 나타난다 — 로컬
병합 브랜치가 origin보다 앞서 있는 한 "푸시가 필요합니다"가 유지되고,
이미 병합된 브랜치 카드에는 **로컬 main에 병합됨 — 푸시 대기** 배지가 붙어
같은 병합을 두 번 하지 않게 막는다.

### 5-e. 끝난 브랜치 정리

병합·push가 끝난 브랜치는 대기 목록에서 사라질 뿐 origin에는 남는다 — 그대로
두면 죽은 feature 브랜치가 쌓여 모두의 브랜치 목록이 어지러워진다. 병합 탭
하단의 **병합이 끝난 원격 브랜치 N개** 카드에서 정리한다.

- 커밋이 **전부 병합 브랜치에 들어간** 브랜치만 후보로 나온다. 지워도 잃는
  코드가 없다.
- 삭제 직전에 한 번 더 확인한다 — 목록을 본 사이 팀원이 새 커밋을 push했다면
  거부된다.
- `.gpconfig`의 병합 대상 브랜치(main, develop 등)는 후보에 나오지 않고,
  요청해도 거부된다.
- 팀원이 지워진 이름으로 계속 작업 중이어도 다시 push하면 브랜치가 새로
  생기므로 사고가 나지 않는다.

## 알림은 어떻게 오는가 (사이드바 → 알림)

`.gpconfig`가 **권한**을 정하는 것과 달리, 알림 화면은 **배달망**을 정한다.
둘을 헷갈리지 않는 것이 중요하다.

| | 어디서 | 무엇을 결정하나 |
| --- | --- | --- |
| **권한** | 저장소 → **설정** 탭 (`.gpconfig`, 저장소에 커밋됨) | 누가 어느 브랜치로 병합·push할 수 있나 |
| **배달망** | 사이드바 → **알림** → 알림 설정 | 누가 어떤 저장소의 소식을 받나 |

알림 화면은 기본적으로 **받은 알림**만 보여 주고, 설정은 접혀 있다. 처음 한 번
이렇게 준비한다:

1. 알림 서버를 띄운다 — 팀에서 한 사람이, 모두가 접속할 수 있는 컴퓨터에서.
   명령은 [README의 "0-1. 팀 서버 띄우기"](../README.md#0-1-팀-서버-띄우기--팀에서-한-사람만-한-번만)에
   그대로 있다. (서버가 없어도 커밋·푸시·병합은 모두 그대로 동작한다. 알림만
   보관되다가 서버가 살아나면 재전송된다.)
2. **알림 설정** → **팀 만들기** → 나온 **참여 코드**를 팀원에게 알려 준다.
   팀원은 같은 화면에서 **참여 코드로 합류**를 누른다.
3. **알림 받을 저장소** — 소식을 주고받을 저장소를 체크한다.
4. **알림 수신자** → **구성원 동기화**. `.gpconfig`에 등록한 구성원을 그대로
   가져온다. **이메일을 두 번 입력하지 않는다** — 사람 목록의 원본은 항상
   `.gpconfig` 한 곳이다.

`.gpconfig`에 없는 사람에게만 알림을 보내야 할 때 **직접 추가**를 쓴다.

## 병합 브랜치는 main이 아니어도 된다

저장소 → **설정** 탭에서 정한다.

- **병합 대상 브랜치**(`merge_targets`) — 병합할 수 있는 브랜치 목록.
  `develop`, `release/1.0` 처럼 여러 개를 둘 수 있다.
- **브랜치별 병합 관리자**(`merge_managers`) — 지정된 사람(과 admin)만 그
  브랜치로 병합하고 push할 수 있다. 다른 사람에게는 버튼이 잠긴다.

이 설정은 `.gpconfig` 파일로 **저장소 안에** 커밋되므로, 같은 프로젝트를 연
모든 사람이 같은 규칙을 본다. 별도 서버 설정이 필요 없다.

푸시 알림 분류도 이 설정을 따른다 — 병합 브랜치가 `develop`이면 `develop`
push가 "새 병합이 반영되었습니다" 알림이 된다. `main`이 하드코딩된 곳은 없다.

## 처음 git 을 쓰는 사람을 위해

앱이 이런 상황을 알아서 안내한다 — 터미널로 나가지 않아도 되는 곳은 앱에서 해 준다.

| 상황 | 앱이 하는 일 |
| --- | --- |
| git 저장소가 아닌 폴더를 골랐다 | **이 폴더를 git 저장소로 만들기** 버튼을 보여 준다 (`.git` 폴더만 생기고 파일은 그대로). 상위 폴더가 저장소면 "혹시 이 폴더를 찾으셨나요?"로 알려 준다. |
| 경로를 `~/projects/app` 로 입력했다 | 홈 경로로 알아서 펼친다. |
| 경로가 없다 / 파일을 골랐다 | 각각 다른 문구로 알려 준다 ("git 저장소가 아닙니다"로 뭉개지 않는다). |
| 커밋이 아직 없다 | 브랜치 칸에 `main (커밋 없음)` 을 보여 주고, "첫 커밋을 만들면 브랜치도 함께 생깁니다"를 안내한다. |
| 원격(origin)이 없다 | 푸시·풀·동기화 버튼을 눌리지 않게 하고, `git remote add origin` 방법을 알려 준다. |
| 커밋할 변경이 없는데 커밋을 눌렀다 | "커밋할 변경이 없습니다"라고 말한다 (예전에는 빈 메시지였다). |
| git 사용자 정보가 없다 | `git config --global user.name/email` 두 줄을 그대로 보여 준다. |
| 푸시가 거부됐다 | "먼저 ‘풀’로 받아온 뒤 다시 푸시하세요" — 원격의 **내 브랜치**에 새 커밋이 있다는 뜻이라 처방은 풀이다 (동기화는 병합 브랜치를 받아오는 버튼). |

파일 상태도 git 용어를 그대로 쓰지 않는다. `untracked` 는 **새 파일**로 적고,
배지에 마우스를 올리면 "git 이 아직 모르는 새 파일입니다"가 뜬다.

## 막혔을 때

| 증상 | 원인과 해결 |
| --- | --- |
| 푸시 버튼이 잠겨 있다 | 그 브랜치에 병합 관리자가 지정되어 있다. 버튼에 마우스를 올리면 누구인지 나온다. |
| "이미 진행 중인 병합이 있습니다" | 병합 탭에서 먼저 마무리하거나 **병합 중단**을 누른다. 진행 중인 병합 위에 새 병합·동기화·풀은 시작되지 않는다 — 풀어 둔 충돌 해결이 날아가지 않게 하기 위한 규칙이다. |
| "검토한 뒤 이 브랜치에 새 push가 있었습니다" | 목록을 보는 사이 팀원이 커밋을 더 올렸거나 히스토리를 다시 썼다. 검토한 것과 병합될 것이 다르면 앱이 멈춘다 — 목록을 새로고침해 최신 내용을 확인하고 다시 병합한다. |
| "지금 브랜치 위에 있지 않습니다(detached HEAD)" | 터미널에서 특정 커밋을 체크아웃한 상태다. 이 상태의 커밋·병합은 어느 브랜치에도 남지 않으므로 앱이 막는다 — 브랜치로 전환한 뒤 다시 시도한다. |
| 앱을 열자마자 로그인을 요구한다 | 요구하지 않는다. 소개 화면에서 **저장소 열고 시작하기**를 누르면 된다. 로그인은 알림·구성원 검색에만 필요하다. |
| 로그인이 안 된다 | 로그인 화면의 **서버 주소**가 맞는지, 그 서버가 떠 있는지 확인한다(`curl <주소>/healthz`). 계정은 서버에 있으므로 서버 없이는 새로 로그인할 수 없다 — 이미 로그인해 둔 상태는 오프라인에서도 유지된다. |
| 구성원 검색에 팀원이 안 나온다 | 그 팀원이 아직 회원가입하지 않았다. 검색은 팀 서버의 회원 목록을 본다. |
| 알림이 안 온다 | ① 알림 서버가 떠 있나 (`cd backend && uvicorn app.main:app`) ② 사이드바 **알림** → 알림 설정에서 팀·저장소·수신자가 채워져 있나 ③ `git-companion`이 `PATH`에 있나 (pre-push hook이 이걸 찾는다 — [HOOKS.md](HOOKS.md)). 기기 등록은 자동이다 — 팀을 만들거나 합류하는 순간 서버에 등록되고, 앱이 5초마다 서버에서 이벤트를 당겨오므로 별도 설정이 없다. |
| 알림의 "리포 보기"가 저장소를 못 찾는다 | 알림은 **origin 원격 주소**로 내 등록 저장소를 찾는다 (폴더 이름이 팀원마다 달라도 된다). 그 저장소의 원격 주소가 팀과 같은지 확인하고, 아직 등록 전이면 등록부터 한다. |
| 자동 해결 결과가 이상하다 | 병합 탭 하단 **백업 복원**으로 원본을 되살리고, 설정에서 지침을 고친 뒤 다시 시도한다. 병합 커밋이 이미 만들어진 뒤에도 24시간 동안 복원 카드가 남는다 — 복원 후 작업 탭에서 변경을 확인하고 새 커밋으로 정리한다. |
| SSH 저장소인데 알림이 없다 | 원격 저장소에는 로컬 hook을 걸 수 없다. 병합 탭의 **자동 감지(20초)**를 켜 두면 새 push가 저절로 올라온다. |
